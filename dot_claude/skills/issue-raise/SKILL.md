# 役割

ユーザーの説明に基づくGitHub Issueの作成

# 入力

- `$ARGUMENTS` に問題や要望の説明が渡される

# 手順

## 1. 内容の整理

- ユーザーの説明を分析
- 必要に応じてコードベースを調査し、関連ファイルや現状の挙動を把握
- 説明が不十分な場合はユーザーに確認

## 2. Issue作成

- `gh issue create`で作成
- タイトル: 簡潔な日本語（30文字以内）
- ラベル: 内容に応じて適切なものを付与（`bug`, `enhancement`等）
  - リポジトリに存在するラベルのみ使用（`gh label list`で確認）
  - 該当するラベルがなければ省略

## 3. body構成

```markdown
## 完了条件

<!-- 何が確認できたらissueをcloseできるのか -->

## 課題

<!-- 現状の実装で起きている課題 -->

## 期待する動作

<!-- あるべき姿。背景と既存仕様は書かない -->

## 背景

<!-- 折りたたみを開かなくても分かる要点 -->

<details>
<summary>詳細な背景</summary>
<!-- 枝葉末節の詳細。不要なら折りたたみだけ省略 -->
</details>

## 仕様

<!-- 折りたたみを開かなくても分かる要点 -->

<details>
<summary>仕様の詳細</summary>
<!-- 枝葉末節の詳細。不要なら折りたたみだけ省略 -->
</details>
```

- `背景`と`仕様`
  - 要点は、各見出しの直下に書く。折りたたみには入れない
  - 枝葉末節の詳細だけを折りたたみに入れる。なければ折りたたみは置かない
- 節自体が不要なら節ごと省略
- bodyにソースの該当箇所（ファイルパス、行番号、関数名）は書かない。実装は変わるため issue が腐る

# 完了条件

- [ ] タイトルが簡潔に30文字以内に留める
- [ ] ラベルがリポジトリ既存のものだけ（該当なしは省略）
- [ ] 折りたたみの外が300〜400文字前後に収めること
- [ ] 折りたたみ外の内容は詳細さより、短い時間で要点が分かる表現であること
- [ ] 背景と決まっている仕様の要点は、見出しの直下にある
- [ ] 折りたたみの中にあるのは、背景と仕様の枝葉末節だけ
- [ ] bodyにファイルパス・ファイル名・行番号・関数名を書いていない
- [ ] 推測で補完せず、不明点はユーザーに確認済み
