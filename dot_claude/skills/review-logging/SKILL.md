# ログ出力レビュー

## 概要

ログは本番環境における**診断インタフェース**。
読者（オンコール担当、上流開発者、サポート、自律エージェント）が、実装を読まずに原因特定と復旧判断ができるかを検査する。

**指摘の基準:** ログが読者の時間を浪費したり、誤った対応を誘発したり、自動化不能なら指摘する。

## 使用すべきとき

- 新規・変更された `log` / `logger` / 診断出力のレビュー
- エラーハンドリング・例外処理・リトライ周辺の変更
- 可観測性・アラート・監視クエリに影響する変更
- 「このログで十分？」「loggingを見て」等の相談

## レビュー手順

1. **対象を列挙** — 追加・変更されたログ出力（レベル、メッセージ、フィールド、出力箇所）
2. **読者を特定** — 誰がいつ読むか（オンコール / 上流SDK利用者 / サポート / エージェント）
3. **シナリオ分類** — 下記5カテゴリのどれか（混同していないか）
4. **3問テスト** — 各ログが「何を試みたか」「誰/何に対して」「なぜ失敗したか」に答えるか
5. **スメル照合** — 下記「ログスメル早見表」で該当パターンを特定
6. **改善案提示** — 指摘ごとに具体的なメッセージ例・フィールド案・出力位置の移動案を示す

## エラーシナリオ分類

ログはまずカテゴリを明示する。
カテゴリが混ざると、読者は誤った復旧行動を取る。

| カテゴリ           | 典型例                             | 読者が取るべき行動             | ログ設計の要点               |
| ------------------ | ---------------------------------- | ------------------------------ | ---------------------------- |
| **システムエラー** | 依存先ダウン、タイムアウト、過負荷 | 後で再試行、エスカレーション   | 一時的か恒久か、再試行可否   |
| **ユーザ無効引数** | 不正入力、存在しないリソース       | 入力修正して再試行             | 入力値をエコー、修正ヒント   |
| **前提条件不成立** | 未ログイン、権限不足、期限切れ     | 別操作（ログイン、権限申請等） | 不足条件と次の一手           |
| **開発者無効引数** | SDK/APIの誤用法                    | 呼び出し元コード修正           | 呼び出し意図と不正パラメータ |
| **アサーション**   | 不変条件違反、到達不能パス         | バグ報告（本番では致命）       | 本番到達は設計バグとして扱う |

## ログスメル早見表

| スメル                 | 検出シグナル                                                       | 問題                                   | 改善の方向                                |
| ---------------------- | ------------------------------------------------------------------ | -------------------------------------- | ----------------------------------------- |
| **実装詳細ログ**       | `ZeroDivisionError`, `NullPointerException`, `underfull hbox` のみ | 読者が実装を理解しないと復旧不能       | プロダクトオントロジーで原因を説明        |
| **一行ログ**           | `error occurred`, `failed`, スタックのみ                           | 操作と入力の文脈が失われる             | 試行操作・入力値・失敗理由を同梱          |
| **文脈欠落**           | 遅延処理・非同期・バッチで入力が記録されない                       | 2日後に意味不明（第3章 foxyloxy 事例） | 配信先リスト、意図した操作を要約          |
| **データ未エコー**     | `User does not exist`（どのユーザか不明）                          | 調査にソースコード参照が必要           | 関連ID・ハンドルをそのまま返す            |
| **理由未説明**         | `does not exist` のみ（非アクティブと区別不能）                    | 誤った優先度判断                       | 詳細理由（deactivated / not found 等）    |
| **非実行可能**         | 原因のみ、次の一手なし                                             | 調査時間の浪費                         | 再試行・修正URL・設定変更手順             |
| **境界外ログ**         | 深い内部層でユーザ文脈なし                                         | ボトムアップ知識しかない               | API/UI/ユースケース境界で再パッケージ     |
| **汎用型乱用**         | すべて `ValueError` / `RuntimeError`                               | 自動ハンドラ・分岐不能                 | カテゴリ別の具体型・エラーコード          |
| **文字列パース依存**   | ログメッセージを正規表現で解析                                     | フォーマット変更で自動化が壊れる       | 構造化フィールド（`user`, `reason` 等）   |
| **情報チェーン断絶**   | 抽象化でハンドルだけ渡し元情報を捨てる                             | 下流ログ改善に大規模リファクタが必要   | ドメインオブジェクトやメタデータを連鎖    |
| **元コンテキスト喪失** | 多段パイプラインで行番号・入力位置消失                             | LaTeX `hbox` 問題と同型                | 各段で診断用コンテキストを保持            |
| **連鎖例外欠落**       | 内部例外を握りつぶし上位だけ出力                                   | 根本原因の特定不能                     | `from error` / `cause` で内部エラーを保持 |
| **レベル不整合**       | アサーションを `warn`、ユーザ入力エラーを `error`                  | アラート疲労または見逃し               | カテゴリとレベルを対応付け                |
| **PII/秘密漏洩**       | トークン・CVV・パスワードを平文出力                                | セキュリティ事故                       | 編集ルールを明示、必要最小限のみ          |
| **過剰ログ**           | 正常系の高頻度詳細ログ                                             | コスト増、シグナル埋没                 | サンプリング、集約、レベル見直し          |

## 診断メッセージの3要素

各エラー/警告ログは、可能な限り次の3問に答える。

1. **何を試みたか** — 操作の要約
2. **誰/何に対してか** — 関連データのエコー
3. **なぜ失敗したか** — プロダクト概念での理由

## 出力位置の原則

**最良のログは、システム知識とユーザ文脈が交わる境界で書く。**

| 手法                 | 向く場面                         | ログ上の期待                               |
| -------------------- | -------------------------------- | ------------------------------------------ |
| **事前妥当性確認**   | 高レベルAPIが呼び出し意図を知る  | 意図 + 不足条件 + 修正URL                  |
| **再パッケージ化**   | 低レベル例外を捕捉して文脈追加   | 内部例外 + 上位メッセージ + 連鎖           |
| **構造化メタデータ** | 自動化・メトリクス・アラート分岐 | フィールドで機械可読、メッセージは人間向け |

## プログラム可能性チェック

上流開発者やエージェントがログ/例外から機械的に分岐できるか。

- カテゴリ別の型・コードがあるか（システム / ユーザ入力 / 前提条件）
- メッセージ解析なしでフィールド取得できるか
- ネスト可能な設計か（SDK → アプリ → ユーザ向けUI）
- ハンドラが「再試行」「ユーザ表示」「開発者通知」を選べるか

## シフトレフト（早期診断）

ログは失敗後だけでなく、**失敗を早く・安く検出する**設計とセットで評価する。

- 静的/低コストチェックで検出できる問題を本番まで持ち込んでいないか
- テスト/フェイク環境で同じ診断品質が再現できるか
- 確認（ドライラン、ヒューリスティック警告）の結果もログに残るか

## 指摘の重大度

| レベル            | 基準                                 | 例                                    |
| ----------------- | ------------------------------------ | ------------------------------------- |
| 🔴 **Critical**   | 障害調査不能、誤アラート、秘密漏洩   | PII平文、一行ログのみ、例外握りつぶし |
| 🟡 **Warning**    | 調査時間増、自動化困難、カテゴリ混同 | 文脈欠落、汎用型、文字列パース依存    |
| 🟢 **Suggestion** | より良い診断体験の余地               | 修正URL追加、フィールド名改善         |

## 出力フォーマット

```markdown
# ログレビュー

## サマリー

- 指摘: Critical N / Warning N / Suggestion N
- 主なリスク: [1行]

### 🔴 [タイトル]

- **箇所:** `path:line`
- **スメル:** [早見表の名称]
- **問題:** [読者への影響]
- **改善案:** [具体的なログ例 or フィールド]

### 🟡 ...
```

## クイックチェックリスト

```
- [ ] 読者（ペルソナ）が特定されている
- [ ] エラーカテゴリがログから判別できる
- [ ] 何を試みたか / 対象 / 失敗理由の3問に答える
- [ ] 関連データがエコーされている（必要なら編集済み）
- [ ] 次の一手または調査手がかりがある
- [ ] 境界（API/ユースケース層）で文脈が最大化されている
- [ ] 構造化フィールドがあり、メッセージ解析に依存しない
- [ ] 内部例外の連鎖が保持されている
- [ ] ログレベルがカテゴリと整合している
- [ ] 秘密情報が出力されていない
```
