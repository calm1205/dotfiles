# 複雑さレビュー（Complexity Review）

## 概要

コードの複雑さ・可読性・保守性をレビューし、**改善指摘のみ**を出力する。
目標は行数を減らすことではなく、読みやすく・理解しやすく・変更しやすく・デバッグしやすいコードへの道筋を示すこと。
すべての指摘は次のテストを通過しなければならない。
「新しいチームメンバーは、指摘どおり直せば元のコードより速く理解できるか？」

## 重要: 指摘のみ

**このスキルはコードを変更しない。**

- ファイルの編集・Write・StrReplace は行わない
- 指摘はレビューコメントとして出力する
- 改善案はコード例で示してよいが、適用はユーザーまたは `code-simplification` スキルに委ねる
- ユーザーが明示的に修正を依頼した場合のみ、別スキル（`code-simplification` 等）を使用する

## 使用すべきとき

- 機能が動作しテストも通ったが、実装が必要以上に重く感じるとき
- コードレビューで可読性や複雑さを評価するとき
- 深いネストのロジック、長すぎる関数、不明瞭な名前に遭遇したとき
- 時間的プレッシャーの中で書かれたコードをレビューするとき
- 重複や不整合を持ち込んだ変更をマージする前

**使用すべきでないとき:**

- コードがすでにクリーンで読みやすい — 指摘のための指摘はしない
- コードが何をしているのかまだ理解していない — レビューの前に理解する
- ユーザーが修正の実施を明示依頼した — `code-simplification` を使用する

## 5つの原則

### 1. 挙動変更を前提にしない指摘

指摘は「どう表現するか」の改善に留める。
挙動を変える可能性がある指摘には、そのリスクを明記する。

```
指摘の前に問う:
→ 提案は同じ入出力・副作用・エラー挙動を保つか？
→ テスト修正が必要になる可能性はないか？
→ 確信が持てないなら、判断を要する旨を記載する
```

### 2. プロジェクトの慣習に従う

指摘は外部の好みではなく、コードベースとの一貫性に基づく。
レビューの前に:

```
1. CLAUDE.md / プロジェクト慣習を読む
2. 近隣のコードが類似パターンをどう扱っているか調べる
3. プロジェクトのスタイルと照合する対象:
   - import の並び順とモジュールシステム
   - 関数宣言のスタイル
   - 命名規則
   - エラーハンドリングのパターン
   - 型アノテーションの粒度
```

プロジェクトの一貫性を壊す指摘は、改善ではない — それは好みの押し付け。

### 3. 賢さより明瞭さを優先する

明示的なコードは、コンパクトな版がパースに一拍の思考を要するなら、コンパクトなコードより優れている。
指摘では「より明瞭な代替案」を示す。

```typescript
// 指摘対象: 密な三項演算子の連鎖
const label = isNew ? 'New' : isUpdated ? 'Updated' : isArchived ? 'Archived' : 'Active';

// 改善案（指摘として提示）: 読みやすいマッピング
function getStatusLabel(item: Item): string {
  if (item.isNew) return 'New';
  if (item.isUpdated) return 'Updated';
  if (item.isArchived) return 'Archived';
  return 'Active';
}
```

### 4. バランスを保つ

過剰な簡素化の指摘も避ける。
次の罠に注意する。

- **インライン化しすぎ** — 概念に名前を与えていたヘルパーの除去は、呼び出し側を読みにくくする
- **無関係なロジックの結合** — 2つの単純な関数を1つにまとめる指摘は、複雑さを増やす
- **「不要な」抽象の除去** — 一部の抽象は拡張性やテスト容易性のために存在する
- **行数の最適化** — 行数の少なさは目標ではない。理解しやすさが目標

### 5. 変更箇所にスコープを限定する

デフォルトでは、レビュー対象の変更差分のみを評価する。
明示的に依頼されない限り、無関係なコードへの指摘は避ける。

## レビューのプロセス

### ステップ1: 触れる前に理解する（チェスタートンの柵）

指摘する前に、それがなぜ存在するのかを理解する。
道を塞ぐ柵を見て、なぜそこにあるのか分からないなら、除去を指摘してはならない。

```
レビューの前に答える:
- このコードの責務は何か？
- 何がこれを呼び、これは何を呼ぶか？
- エッジケースとエラー経路は何か？
- 期待される挙動を定義するテストはあるか？
- なぜこう書かれた可能性があるか？（性能？ プラットフォーム制約？ 歴史的理由？）
- git blame を確認する: このコードの元の文脈は何だったか？
```

これらに答えられないなら、指摘の準備はできていない。
先に文脈をもっと読む。

### ステップ2: 複雑さのパターンを特定する

次のパターンを走査する — それぞれが具体的なシグナルであり、漠然とした「におい」ではない。

**構造的な複雑さ:**

| パターン | シグナル | 改善案（指摘内容） |
|---------|--------|----------------|
| 深いネスト（3階層以上） | 制御フローを追いにくい | 条件をガード節やヘルパー関数に抽出 |
| 長い関数（50行以上） | 複数の責務 | 説明的な名前を持つ焦点の絞られた関数に分割 |
| ネストした三項演算子 | パースに脳内スタックが必要 | if/else 連鎖、switch、ルックアップオブジェクトに置換 |
| 真偽値のパラメータフラグ | `doThing(true, false, true)` | オプションオブジェクトや個別の関数に置換 |
| 繰り返される条件 | 複数箇所で同じ `if` チェック | 名前の付いた述語関数に抽出 |

**命名と可読性:**

| パターン | シグナル | 改善案（指摘内容） |
|---------|--------|----------------|
| 一般的すぎる名前 | `data`, `result`, `temp`, `val`, `item` | 中身を表す名前に変更: `userProfile`, `validationErrors` |
| 省略された名前 | `usr`, `cfg`, `btn`, `evt` | 省略が普遍的（`id`, `url`, `api`）でない限り完全な単語を使う |
| 誤解を招く名前 | `get` という名前なのに状態も変更する関数 | 実際の挙動を反映した名前に変更 |
| 「何を」を説明するコメント | `count++` の上の `// increment counter` | コメントを削除 — コードが十分に明瞭 |
| 「なぜ」を説明するコメント | `// 負荷時に API が不安定なためリトライ` | 残す — コードでは表現できない意図を運んでいる |

**冗長性:**

| パターン | シグナル | 改善案（指摘内容） |
|---------|--------|----------------|
| 重複したロジック | 複数箇所に同じ5行以上 | 共有関数に抽出 |
| デッドコード | 到達不能な分岐、未使用変数、コメントアウトされたブロック | （本当に死んでいると確認のうえ）削除 |
| 不要な抽象 | 価値を加えないラッパー | ラッパーをインライン化し、下層関数を直接呼ぶ |
| 過剰設計のパターン | ファクトリのためのファクトリ、単一戦略のストラテジ | シンプルな直接的アプローチに置換 |
| 冗長な型アサーション | すでに推論済みの型へのキャスト | アサーションを削除 |

### ステップ3: 指摘を構造化して出力する

コードは変更せず、レビューコメントとして出力する。

**指摘フォーマット（各項目）:**

```
### [重要度: 高/中/低] 指摘タイトル
- **場所:** ファイルパス:行番号
- **問題:** 何が複雑か・読みにくいか
- **改善案:** 具体的な代替アプローチ（コード例可）
- **根拠:** なぜ改善になるか
- **注意:** 判断を要する場合や挙動リスクがある場合
```

**優先度の目安:**

| 重要度 | 基準 |
|-------|------|
| 高 | バグ混入リスク、理解コストが著しく高い、重複が3箇所以上 |
| 中 | 可読性・保守性の改善、局所的な複雑さ |
| 低 | 好みに近い、将来の拡張時に検討で十分 |

**出力の原則:**

- 指摘は優先度順に並べる
- 改善案は1指摘1案 — 複数の選択肢がある場合は判断を要する旨を記載
- 問題がなければ「複雑さの指摘なし」と明示する
- 修正の実施は促さない — 指摘で終わる

### ステップ4: 指摘の品質を検証する

出力前に自己チェックする。

```
指摘の品質チェック:
- 各指摘は具体的な場所と問題を示しているか？
- 改善案はプロジェクト慣習に沿っているか？
- チェスタートンの柵を適用し、理由不明のコードを不用意に指摘していないか？
- 指摘どおり直しても挙動が変わらないと確信できるか？
- スコープ外のコードに指摘していないか？
```

## よくある自己正当化

| 自己正当化 | 現実 |
|---|---|
| 「動いてるんだから指摘不要」 | 読みにくいコードは、壊れたときに直しにくい。指摘は将来の変更コストを下げる。 |
| 「行数が少ないほど常に簡潔」 | 1行のネストした三項演算子は、5行の if/else より簡潔ではない。 |
| 「ついでに無関係なコードも指摘しよう」 | スコープ外の指摘はノイズになり、レビューの焦点を失う。 |
| 「指摘しつつ修正もしておこう」 | このスキルの役割は指摘のみ。修正は `code-simplification` に委ねる。 |
| 「元の作者には理由があったはず」 | git blame を確認し、チェスタートンの柵を適用する。 |

## レッドフラグ（指摘側）

- 場所の特定なしに漠然とした指摘
- プロジェクト慣習ではなく自分の好みに基づく指摘
- 完全には理解していないコードへの除去指摘
- 指摘と同時にコードを変更してしまう
- 依頼されていないスコープ外コードへの指摘

## 検証

レビュー出力の完了後:

- [ ] コードファイルは一切変更していない
- [ ] 各指摘に場所・問題・改善案が含まれている
- [ ] 優先度が付与されている
- [ ] スコープ外の指摘がない
- [ ] 判断を要する指摘には注意書きがある
- [ ] 問題がなければ「指摘なし」と明示している
